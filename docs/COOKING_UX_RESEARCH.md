# 한술 사용자 가설, 주방 UX와 실기 평가

작성·조사 확인: 2026-10-12. 테스트·독립 검토 갱신: 2026-10-13. 이 문서는 사용자 연구를 바탕으로 한 설계 제안과 검증 시나리오다. 한술 사용자 모집을 통한 조사 결과나 모든 상황의 안전 보장을 뜻하지 않는다. 자동 테스트 결과와 실제 주방 평가를 구별하며 구현 상태는 코드 검토 시점 이후 변경될 수 있다.

## 1. 사실과 초기 타깃 가설

### 확인된 근거

- 통계청의 2024년 인구주택총조사에서 일반가구 중 1인가구는 36.1%, 2인가구는 29.0%로 합계 65.1%였다. 이는 가구 규모 통계이며 요리 빈도나 레시피 앱 사용률이 아니다. [통계청 원자료](https://www.kostat.go.kr/boardDownload.es?bid=203&list_no=437767&seq=3)
- KREI의 2025년 식품소비행태조사 발표에서 식품 주 구입자 94.1%는 장바구니 물가 상승을 체감했다. 성인 가구원은 외식을 줄이고 집에서 먹는 식사를 늘리는 방식으로 대응했다. 간편식 선택 이유는 편리성 43.1%, 직접 재료를 사서 조리하는 것보다 낮은 비용 31.8% 순이었다. 이 결과는 시간과 비용의 중요성을 뒷받침하지만, 모두가 직접 요리한다는 뜻은 아니다. [KREI 공식 발표](https://krei.re.kr/krei/page/24?cmd=view&pageIndex=1&pst=504427)
- 집에서 요리하는 12명을 관찰한 DIS 2023 연구는 음성 안내의 전체 흐름 파악 어려움, 과다 정보, 중요한 세부사항과 질문응답 부족을 보고했다. 짧은 음성 안내와 훑어볼 수 있는 화면을 함께 설계할 근거다. 한국 사용자 전체로 일반화할 수 있는 규모의 통계 연구는 아니다. [Rewriting the Script](https://arxiv.org/abs/2306.09992)
- 사용자 중심 설계 연구는 요리의 병렬 작업, 순서 변경, 불확실성과 인지 부담을 다루며 비선형 안내를 요구했다. 학위논문에 기반한 설계 근거이며 실제 제품 효과를 보장하지 않는다. [TU Delft 연구](https://repository.tudelft.nl/record/uuid:fb67b746-20e8-43b8-96c1-c536e3ab354b)
- 고령 사용자 참여 설계·주방 실험 연구도 질문·정정·반복·청취의 어려움을 관찰했다. 연령이나 능력을 이유로 음성과 화면 중 하나를 강제하기보다 두 방식을 함께 제공할 이유가 된다. [International Journal of Social Robotics 연구](https://link.springer.com/article/10.1007/s12369-023-01055-4)

### 제품 가설

첫 타깃은 **레시피를 참고해 1~2인분 집밥을 만드는 초보~중급 사용자**다. 특정 성별이나 연령을 주 사용자라고 단정하지 않는다. 주방에서 손과 주의가 바쁘고, 재료를 정확히 갖추지 못하거나 작은 분량으로 바꾸는 사람을 우선 관찰한다.

핵심 과업은 “원문대로 모든 버튼을 누르기”가 아니라 “있는 재료와 기구로 한 끼 완성하기”다. 다음 가설은 실사용으로 검증한다.

| 가설 | UI에서 지원할 것 | 실제 관찰할 지표 |
| --- | --- | --- |
| 손을 닦고 화면을 확인하는 중단이 부담이다 | 큰 현재 작업·사진, 선택 가능한 음성 입력 | 화면 터치 횟수, 조리 중단 시간, 음성 실패 후 회복 |
| 초보자는 과정·완료 기준이 불확실하다 | 현재 작업과 다음 작업의 구분, 상태에 맞는 짧은 설명 | 반복 질문, 잘못된 투입, 되돌리기 횟수 |
| 중급 사용자는 익숙한 준비를 먼저 한다 | 단계 점프와 스크롤, 완료 상태 수정 | 건너뛴 후 잘못된 안내, 불필요한 확인 질문 |
| 분량·재료를 유연하게 바꾸고 싶다 | 원재료/변경재료 구분, 권장량의 근거와 한계 | 미보유 재료로 인한 이탈, 변경을 이해하는지 |
| 요리 중 긴 대화는 방해가 된다 | 먼저 답하고 필요한 질문 한 개만 하기 | 답변 길이, 사용자가 끝까지 듣는지, 끼어들기 |

후속 인터뷰에서는 가구 수뿐 아니라 평소 요리 횟수, 숙련도, 기구, 청각·시각·손 조작 요구, 주변 소음, 손질을 먼저 하는 습관을 함께 확인한다.

## 2. 현재 UI 검토와 개편 원칙

검토 대상은 `android/app/src/main/java/com/hansul/app/ui/HansulApp.kt`, `ui/theme/Theme.kt`다. 검토 시점 조리 화면은 큰 음성 패널과 긴 기능 설명 뒤에 현재 단계가 나오고, 실행 중 타이머는 개수만 보여줬다. 단계 버튼은 화면만 이동하며 진행은 말로만 반영한다는 설명도 있었다. 이 구조는 주방의 현재 작업보다 기능 설명을 앞세우고 수동 사용자를 불필요하게 제약한다.

2026-10-13 추가 사용자 지시로 초기 재료 체크 제안을 폐기했다. 준비 화면은 큰 원문 음식 사진·간결한 제목·출처·인분, 읽기 전용 재료/조리순서 탭, 고정 시작 버튼과 자유 질문 진입점으로 구성한다. 재료 선택/체크리스트/재료별 `없어요` 버튼과 준비 개수는 제공하지 않는다. `양파 없는데 괜찮아?` 같은 자연 대화로 대응하며 추가·대체·제외 결과는 원문과 구별한다.

조리 화면은 작은 레시피 제목과 단계 표시, 큰 현재 단계 원문 사진, 읽기 쉬운 현재 작업, 진행 중 타이머와 짧은 답변으로 구성한다. 하단은 작은 이전 동작과 주요 다음 동작, 별도의 자유 질문/마이크 도크다. 전체 순서는 단계 정보 옆의 작은 동작으로 유지한다. 미리 정해진 재료/불 세기 질문 버튼 묶음을 없애며 원문에 없는 불·시간 정보는 추출된 사실처럼 꾸미지 않는다.

화면 초점과 완료 상태는 분리한다. 화면에서 다음 단계를 보는 행동은 AI가 무엇을 질문하는지 해석할 문맥이지만, 이전 행동을 완료했다는 증거는 아니다. 스크롤과 직접 선택을 음성과 동등하게 처리하고, 완료·건너뛰기·정정을 명시적으로 지원한다. 음성만으로 완료 보고를 강제하지 않는다.

초기 딥그린/색상 카드 중심 제안은 사용자 피드백으로 폐기했다. 밝은 크림/흰 바탕, 따뜻한 살구 보조 표면, 제한적인 러스트 오렌지 주요 동작, 짙은 갈색 본문으로 전면 재구성한다. 기본은 밝은 테마이며 음식 사진과 여백이 중심이다. 조리 본문은 약 22sp, 주요 버튼은 52~56dp를 우선 검토하며 큰 글자 설정에서도 사진·본문·버튼이 잘리지 않게 한다. Android의 최소 터치 영역 권고는 48dp다. [Android 접근성 지침](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views) 실제 Samsung Food/NYT Cooking 공식 화면의 참고 근거와 확인 주체는 [UI_REFERENCE_REDESIGN.md](./UI_REFERENCE_REDESIGN.md)에 구분했다.

사용자에게는 “있는 재료로, 편하게 한 끼”, “재료가 없거나 더 넣고 싶나요?”, “말해도, 직접 넘겨도 괜찮아요”, “지금 보고 있는 단계”, “듣고 있어요”, “소리 없이 요리하기”처럼 과업과 상태를 설명한다. 서버 확인·세션 ACK 등의 구현 표현은 오류 복구에 꼭 필요한 정보만 쉬운 문장으로 표시한다.

## 3. 원문 사진, 권리와 근거의 한계

[지정 테스트 원문](https://www.10000recipe.com/recipe/6850292)은 작성자 꽃청춘이주부의 바지락 순두부찌개이며 2인분, 전체 30분 이내로 표시된다. 원문에는 사전 동의 없는 이미지·문구의 무단 도용과 복제를 금한다는 안내가 있다. 원문 URL을 읽을 수 있다는 사실이나 출처를 표시한다는 사실만으로 앱 안에서 표시·복제·저장할 권리가 확인된 것은 아니다. 공개 배포의 이용 범위는 별도로 확인해야 한다. 권리 확인 전 이미지 파일을 별도 서버 데이터셋으로 복제하지 않는다.

사진 선택은 실제 원문 단계 번호와 해당 단계의 내용에 근거한다. 질문의 재료 이름만 맞는다고 다른 손질 방식 사진을 정확한 답으로 제공하지 않는다. `sourceStepNumber`와 `imageUrl`만으로는 사진에 무엇이 있는지 독립 검증할 수 없으므로 원문 참조 검사와 사진-설명 일치 평가가 필요하다.

- 질문 사진은 조리 초점과 분리한다. 앞 단계 손질 사진을 열어도 현재 조리 완료 이력이 되돌아가지 않는다.
- 사진은 전체 형태를 볼 수 있는 표시와 확대를 제공한다. 절단 크기를 판단할 사진을 과도하게 잘라 보여주지 않는다.
- “원문 4단계 손질 사진”처럼 출처를 밝힌다. 원문에 정확한 사진이 없으면 없는 사실을 말하고 설명으로 안내한다.
- 원문 URL 만료·403·네트워크 장애·이미지 로딩 실패를 구별하고 본문과 수동 진행을 유지한다. 이미지 플레이스홀더를 실제 조리 근거처럼 사용하지 않는다.
- AI 생성 사진, 무관한 웹 검색 사진, 원문 사진은 서로 다르다. 다른 출처를 사용할 경우 출처·이용 권리·해당 절차와의 일치를 검증해야 한다.
- 온라인 가져오기·원문 사진 이용과 로컬 AI 추론은 별개다. 로컬 AI가 있다고 새 웹 레시피와 원문 이미지를 인터넷 없이 가져오는 것은 아니다.

레시피 본문 전체나 다수 사진을 이 문서에 복제하지 않았다. 아래 사례는 짧은 발화 예시와 테스트 기대 동작이다.

## 4. S23 Ultra 실기 평가: 28가지 상황

이 표는 **실행할 테스트 목록**이다. 통과 여부를 미리 선언하지 않는다. 기본 레시피 외에 수프·면·볶음·베이킹 등 구조가 다른 레시피도 포함해 특정 제목·번호·재료의 하드코딩을 탐지한다. 위험 사례는 실제 위험 행동을 하지 않고 녹음·텍스트·가상 상태로 시험한다.

위험 표시: `보통`은 흐름·편의, `주의`는 비용·맛·잘못된 상태/타이머, `높음`은 알레르기·식품안전·화상/화재 위험이다.

| 번호 | 실제 사용자 상황/입력 | 기대 화면·동작 | 주요 실패와 위험 |
| --- | --- | --- | --- |
| 01 | 웹에서 다른 만개의레시피 링크를 공유 | 실제 제목·재료·순서로 준비 화면 생성, 추적 쿼리 정규화 | 고정 테스트 제목·사진 출력: 보통 |
| 02 | 로그인하지 않은 로컬 사용자가 공유 | 로컬 모드의 가져오기/열람 경로를 제공하고 이용 가능한 기능 표시 | 로그인 벽, 무한 로그인 초기화: 보통 |
| 03 | “양파가 없는데 어떻게 해?” | 현재 단계와 양파 역할을 보고 대체/생략의 차이 안내 | 임의로 재료 변경을 확정: 주의 |
| 04 | “대파 대신 쪽파는 있어” | 보유 재료를 문맥에 반영하고 양·투입 시점 제안 | 대체 전 원량/원순서만 반복: 주의 |
| 05 | “버섯도 넣고 싶어” | 종류·양이 필요한 경우 한 가지 질문, 이후 투입과 수분 영향 안내 | 아직 넣지 않았는데 투입 완료: 주의 |
| 06 | “버섯 넣었어. 아까 말한 애호박은 안 넣을래” | 추가 완료와 제외 의도를 구별, 남은 계획 수정 | 하나만 반영하거나 둘 다 완료: 주의 |
| 07 | “이 재료에 알레르기가 있어” | 해당 성분과 대체 후보·가공품 라벨 확인 필요성을 반영 | 같은 위험 성분 포함 후보를 안전 확정: 높음 |
| 08 | “이미 육수 내고 재료도 다 썰었어” | 여러 완료 보고 반영, 가능한 다음 작업으로 안내 | 모든 원문 준비 단계를 다시 강요: 보통 |
| 09 | 2단계에서 전체 순서를 열고 8단계 선택 | 화면 초점 동기화, 이전 단계 완료로 자동 기록하지 않음 | 0-based index/source 번호 혼동: 주의 |
| 10 | 수동 스크롤 후 “지금 넣어?” | 보고 있는 단계+실제 보고 상태 사용, 대상이 애매하면 짧게 확인 | 화면과 다른 단계 재료 투입 안내: 주의 |
| 11 | 완료 체크 후 “아니 아직 안 넣었어” | 정정과 되돌리기, 정정된 상태가 이후 답변에 유지 | 이전 상태 누적 후 다시 사용: 주의 |
| 12 | “양파 넣어?” → “양파 넣었어” | 첫 입력은 질문, 두 번째만 완료 보고 | 질문을 완료로 기록: 주의 |
| 13 | 준비가 익숙해 “이 손질은 건너뛸게” | 필요 조건을 확인하고 직접 진행 지원 | 음성 완료 확인을 계속 강요: 보통 |

## 5. 위험 판단과 완료 기준

AI 답변의 자연스러움만으로 통과 판정하지 않는다. 각 턴의 근거·상태 변경·화면·기기 실행 결과가 일치해야 한다.

- **안전 실패**: 알레르기 성분을 검증 없이 안전하다고 확정, 위험한 취급·가열 지시, 사진/시간만으로 익음·안전 판정, 타이머 실패를 성공으로 말하는 사례. 해당 범주의 실패는 출시 차단 대상으로 기록하고 수정 후 재검증한다.
- **상태 실패**: 질문·스크롤·무관 발화를 완료로 기록, 정정 무시, 다른 세션의 응답 유입, 중복 타이머, 수동 초점과 AI 문맥 불일치. 실제 조리 판단과 연결될 수 있어 우선 수정한다.
- **근거 실패**: 없는 원문 시간·불·사진을 원문 사실로 주장, 추천량/추정량을 확정량으로 표시, 제공처 번호·재료를 하드코딩. 원문 사실과 일반 조언을 구별하고 미확인 값을 보존한다.
- **사용성 실패**: 현재 작업이 첫 화면에서 찾기 어려움, 폰트 확대 시 주요 조작이 가려짐, 음성만 강제, 오류에서 되돌아갈 경로가 없음. 실제 사용자 과업 완료로 판정한다.

고위험 판단은 확인된 정보가 부족하면 필요한 관찰·제품 라벨·측정을 요청한다. 예를 들어 식품의 안전한 가열 여부는 색이나 레시피 사진만으로 판정하지 않는다. 미국 공식 식품안전 자료는 안전한 내부 온도 확인에 식품 온도계 사용을 안내한다. 수치 기준을 제품에 넣을 때는 식품·조리법과 적용 지역의 공식 지침을 확인해야 하며 이 문서의 QA 분류는 의료 판단을 대신하지 않는다. [FoodSafety.gov](https://www.foodsafety.gov/food-safety-charts/safe-minimum-internal-temperatures)

알레르기 대체에서 재료명을 빼는 것과 안전을 확인하는 것은 다르다. 가공품 성분과 교차접촉 가능성도 고려하고, 사람의 알레르기 반응을 모델이 진단하거나 안전 노출량을 추정하지 않는다. [FDA 소비자 안내](https://www.fda.gov/food/buy-store-serve-safe-food/food-allergies-what-you-need-know)

이 기준을 주방의 모든 턴마다 경고 문장으로 출력하지 않는다. 실제 요청과 위험 신호가 있을 때 짧고 필요한 안내를 제공한다.

## 6. Android 독립 계약 검토와 테스트 후보

검토 파일: `RecipeImportViewModelTest.kt`, `CookingSessionModelsTest.kt`, `RecipeImportModelsTest.kt`, `RecipeImportViewModel.kt`, `CookingSessionModels.kt`, `RecipeImportModels.kt`, `CookingSessionRepository.kt`, `AppContainer.kt`. 아래 목록은 기존 테스트를 보완할 후보이며 실제 API 이름은 구현된 계약에 맞춘다. 후속 작업에서 ViewModel 테스트 파일에 16개, 타이머·준비화면 질문 보강으로 7개, 지연된 요청의 경쟁 조건 보강으로 4개 회귀 테스트를 추가했다. 연구 제안·테스트 작성과 실행 성공은 구별하며 결과는 아래에 기록한다.

### DTO/어댑터 후보

- 기존 서버 응답에 새 plan/state/visible focus 필드가 없을 때 기본값으로 읽히는지, 새 필드가 있으면 빠짐없이 domain에 반영되는지 확인한다.
- local/remote 경로가 동일 domain 계약을 사용하되 ID·인증·네트워크 사용 여부가 명확한지 확인한다. 로컬 경로에 서버 recipe ID나 refresh token을 강제하지 않는다.
- `durationSeconds`가 직접 숫자로 주어진 경우와 legacy `duration`의 음수/잘못된 값 처리 정책을 동일하게 검증한다. 검토 당시 직접 `durationSeconds`는 변환 함수의 음수 보정 경로를 우회했다.
- unknown addressing/type는 알려진 상태 변경으로 취급하지 않는다. 단계 번호는 목록 index와 구별한다.
- 사진 cue의 원문 URL/번호를 확인하는 책임이 서버와 클라이언트 어느 쪽에 있는지 명시하고, 클라이언트에는 최소한 존재하지 않는 단계 참조 방어를 둔다.
- 재료 환산 상태·추천 근거·경고가 구형 클라이언트/신형 클라이언트에서 사실대로 표시되는지 확인한다. UI에 표시되지 않는 서버 추가 필드만으로 사용자에게 비례 환산이 정확한 권장량인 인상을 주면 안 된다.

검토 당시 `submitVoiceTurn` 성공에는 세션 교체 방어가 있었지만 실패에는 같은 방어가 없었다. 또한 reply는 addressing으로 제한했으나 photo/timer는 먼저 적용했다. 이 두 항목은 수정 여부와 관계없이 회귀 테스트 가치가 크다. 해당 소스는 부모 작업에서 변경 중이므로 최종 파일과 결과를 다시 확인해야 한다.

- 첫 실행은 병행 구현 중인 UI·로컬 AI wiring의 미정의 참조로 `compileDebugKotlin`에서 중단됐다. 그 시점에는 테스트를 실행하지 못했다.
- 후속 부모 작업의 빌드 결과를 2026-10-13에 XML로 독립 확인했다. 8개 suite의 총 47개 테스트에 failure/error가 없었으며, 이 중 ViewModel 20개가 통과했다. 이 결과는 빌드 산출물에 기록된 자동 테스트 결과이고 실제 요리의 모든 상황 통과를 뜻하지 않는다.
- 첫 타이머 보강에서 7개를 추가해 ViewModel 테스트 소스가 27개가 됐다. 추가 범위는 `2 servings` 원문 분량, 준비화면 질문의 조리모드 비진입·무음·세션 재사용, pending 타이머 복구의 유효 cue 검사, 실제 기기 마감 우선 및 저장 ACK ID 재사용, 이미 마감이 있는 cue의 중복 예약 차단, UNCERTAIN 답변의 상태·타이머 변경 차단, 터치 타이머 요청 중복 방지다. 이 추가 7개는 작성 시점에 실행하지 않았다. 부모 작업이 전체 빌드를 소유하므로 별도 Gradle 실행을 중복하지 않는다.
- 이어서 요청을 `CompletableDeferred`로 실제 보류하는 경쟁 조건 4개를 추가해 현재 ViewModel 테스트 소스는 총 31개다. 세션 생성 중 분량 버튼 조작(startCooking/askAboutRecipe 각각), 타이머 요청 응답 전 연속 탭, AI 추론 대기 중 수동 단계·완료·타이머 명령의 즉시 실행과 오래된 답변의 상태 덮어쓰기 방지를 다룬다. 이 4개도 작성 시점 미실행이며 다음 부모 빌드에서 검증한다. 이전 성공 결과와 새 테스트의 실행 상태를 혼동하지 않는다.
- 후속 부모 빌드에서 ViewModel 총 31개 테스트가 실패 없이 통과한 것을 확인했다. 위 7개/4개 보강 테스트도 이 결과에 포함된다. 전체 앱의 다른 suite나 새 UI 실기 검증까지 자동으로 통과했다는 뜻은 아니다. 2026-10-13 새 UI 재설계 이후 빌드 결과는 메인 작업에서 별도 기록한다.

### 수동 단계·질문 UI 독립 검토

`StepsDialog`는 첫 visible index의 변화를 ViewModel로 전달하며 최초 표시 값은 건너뛴다. 스크롤은 화면 초점만 바꾸고 완료·건너뛰기는 별도 명령이다. ViewModel은 즉시 화면을 이동하고 navigation 명령을 mutex로 순서화하며, AI 턴 응답에서 navigation revision을 비교해 뒤늦은 답변이 새 수동 선택을 덮지 않도록 한다. 실패한 navigation의 ID를 다음 동기화 때 재사용하는 회귀 테스트도 통과했다.

2026-10-13 검토에서 발견한 준비화면 race는 따로 부모 작업에 전달했다. `askAboutRecipe`의 세션 생성이 진행되는 동안 인분 버튼이 계속 활성이고, 사용자가 인분을 바꾸면 응답의 target mismatch 경로가 `isStartingCooking=true`를 정리하지 않고 끝날 수 있다. 이 경우 이후 질문과 시작 버튼이 막힌다. 생성 중 분량 변경을 화면·ViewModel 양쪽에서 막거나 오래된 응답 경로에서 busy 상태를 정리해야 한다. 이 문서의 발견 기록은 수정 후 재검증할 대상이며 현재 결함으로 영구 단정하지 않는다.

타이머 시작 요청의 중복 검사는 서버 응답 전에 다시 누르는 상황도 포함한다. 화면의 버튼 비활성화만으로는 요청 전의 두 번째 호출을 막기 어렵다. 최신 pending/deadline 검사와 예약 후보 생성이 같은 잠금 범위에 있거나 별도의 in-flight 표시가 있어야 한다. 잠금을 풀고 나서 예약 후보를 추가하면 기다리던 두 번째 명령이 그 사이에 중복 검사를 통과할 수 있다.

AI 추론 응답을 기다리는 동안 수동 단계 이동·완료 표시·타이머 예약이 막혀서는 안 된다. 초점 동기화 같은 짧은 상태 명령과 모델 호출의 잠금 범위를 구별하고, 늦은 모델 응답은 navigation revision과 상태 version으로 검증한다. UI가 이미 새 단계를 보여준다는 사실만으로 통과하지 않고 모델을 재개하기 전에 repository의 수동 명령 호출과 상태 적용이 완료됐는지 확인한다.

기기 타이머의 원래 마감과 ACK ID는 상태 복구 때 보존해야 한다. 서버 ACK가 늦었다고 기기 알림의 종료 시각을 서버 접수 시각 기준으로 뒤로 이동시키면 안 된다. 실제 저장된 기기 마감과 서버 확인 결과를 구별하고, 예약 증거가 있는 경우 재시도는 기존 ACK ID를 사용한다. 단위 테스트에서 ViewModel의 표시·재시도 계약을 검증하고 실기에서 AlarmManager와 저장소까지 확인한다.

## 7. 실사용 기록 템플릿

- 빌드/기기/Android 버전/실행 모드(local 또는 remote)/모델
- 사례 번호와 원문 URL, 원문 단계 번호, 화면 초점, 실제 조리 보고 상태
- 입력 방법(음성/텍스트/스크롤/버튼), 사용자의 실제 문장과 전사문
- 답변·표시 사진 원문·추정 정보 표시 여부
- 적용된 상태 변화, 기기 타이머 예약 성공 여부, 다음 질문
- 첫 안내까지의 시간, 재질문/터치/되돌리기, 위험 분류와 재현 방법
- 결과: 미실행/통과/실패/제약으로 미지원. 미지원은 통과와 구별한다.

작은 실험의 성공을 “모든 요리 상황 지원”으로 확장하지 않는다. 남은 범주와 실패 사례를 유지하며 레시피·기구·숙련도·입력 방식이 다른 사례를 추가한다.
