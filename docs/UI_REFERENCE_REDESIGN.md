# 한술 UI 전면 재설계: 실제 제품 참고와 적용안

확인일: 2026-10-13. 이 문서는 연구/설계 제안이며 UI 소스 수정 내역이 아니다.

## 이번 사용자 요구가 우선인 결정

- 재료 선택, 재료 체크박스/체크리스트, 재료별 `없어요` 버튼을 제거한다. 조리를 시작하려고 재료 상태를 입력하게 하지 않는다.
- `양파 없는데 괜찮아?`, `지금 버섯 넣어도 돼?` 같은 자연 발화/텍스트 질문으로 대체·생략·추가를 다룬다. 별도 재료 편집 도구의 사용을 강요하지 않는다.
- 단순 색상 교체가 아니라 홈→레시피→조리 화면의 정보 우선순위와 구성 자체를 바꾼다. 밝고 식욕을 돋우는 파스텔 톤, 음식 사진, 한 번에 보이는 핵심 작업이 중심이다.
- 화면 스크롤/단계 선택은 음성과 동등한 입력이다. 단계 조회와 실제 완료는 구별하고, 사용자가 매 단계를 말해야 한다고 가정하지 않는다.

## 근거를 확인한 범위와 한계

공식 제품 페이지, 공식 도움말, 공식 스토어 등록 스크린샷 링크를 조사했다. 아래에서 **공식 기능/구성 확인**, **스크린샷 검색 결과의 시각 설명**, **한술의 새 제안**을 구분한다. 다른 앱의 현재 동작을 직접 로그인하여 사용한 것은 아니다.

담당 연구 에이전트의 computer-use 인벤토리는 `apps=[]`, `browsers=[]`였고 인앱 브라우저도 사용할 수 없었다. 이 에이전트는 검색 도구가 반환한 실제 스크린샷의 시각 설명과 공식 문서로 구성/동작을 교차 확인했다. 반면 **메인 에이전트는 브라우저에서 Samsung Food 공식 Add Recipe 화면과 NYT Cooking Google Play 갤러리를 실제로 보고 확인**했다. 아래에 확인 주체를 구분한다. 다른 앱을 설치/로그인하여 조리하지 않았으며 정확한 픽셀 크기나 색상값을 측정한 것도 아니다. Kitchen Stories 공식 CDN의 브라우저 차단은 우회하지 않았고 기능 설명 문서만 근거로 쓴다.

## 실제 제품에서 가져올 세 가지 패턴

### 1. Samsung Food: 음식 사진과 레시피 제목이 먼저, 세부 기능은 뒤

메인 에이전트는 Samsung Food 공식 `Add Recipe` 화면을 실제 브라우저에서 확인했다. 흰 바탕, 검은 본문, 둥근 오렌지 `Save` 버튼, 사진 영역과 Description의 분명한 위계가 관찰됐다. 이는 대형 버튼/색상 카드가 여러 개 경쟁하는 구성 대신 음식 콘텐츠와 한 가지 주요 동작을 중심에 두는 참고다. [공식 레시피 관리 소개](https://samsungfood.com/recipe-box-app/), [메인이 실제 확인한 Add Recipe 이미지](https://samsungfood.com/wp-content/cache/thumb/80/1dbede8fe37fa80_381x607.jpg). 공식 페이지의 첫 번째 hero는 원문 블로그 가져오기 설명용 목업으로 삼성 앱 자체 화면이 아니므로 삼성 앱 디자인 근거에서 제외했다.

별도로 공식 Galaxy Store 등록 스크린샷의 검색 결과는 `Healthy Spinach Pasta`의 큰 사진/제목/작성자, 사진 아래 재료·조리시간·건강정보 탭을 설명했다. 이 부분은 **연구 에이전트가 받은 스크린샷 시각 설명**이며 직접 픽셀 검증과 구분한다. [공식 Galaxy Store 등록 페이지](https://galaxystore.samsung.com/detail/com.foodient.whisk), [등록 스크린샷 원본 링크](https://img.samsungapps.com/productNew/000004687198/ENG/ScreenShot_20250526122336226_1656_3312_1.png).

삼성의 공식 도움말은 재료·조리순서·건강정보의 세 탭, 인분/단위 변경, 작성자 사이트 연결을 확인해 준다. 외부에서 저장한 레시피의 많은 조리순서는 작성자 사이트에 남겨둔다는 설명도 있다. **탭 구조와 기능은 공식 문서로 확인한 사실**이다. [Samsung Food Recipe Page 101](https://support.samsungfood.com/hc/en-us/articles/18588916048276-Recipe-Page-101).

한술에 적용할 원칙: 사진→제목→인분/시간→`요리 시작`이 한눈에 읽히는 요리 앱을 만든다. 로그인, 서버 주소, 모델 상태, 길게 늘어선 도구 버튼, 장문의 AI 기능 소개가 먼저 보이는 개발자 도구형 화면을 피한다. 삼성의 건강정보/커뮤니티/쇼핑 같은 넓은 기능 집합을 그대로 가져오지는 않는다.

### 2. Kitchen Stories: 조리 모드는 단계별 사진과 지시를 묶는다

공식 앱 소개는 조리 모드에서 단계별 사진과 지시를 함께 제공하고, 기술 설명 영상/팁도 제공한다고 명시한다. 공식 App Store 소개 역시 고품질 사진을 포함한 단계별 지시를 설명한다. **단계 사진+현재 지시가 하나의 묶음이라는 제품 기능은 확인**했지만 이 세션에서 CDN 조리 화면의 정확한 버튼 배열은 직접 확인하지 못했다. [공식 앱 소개](https://pages.kitchenstories.com/en/app), [공식 App Store 등록 페이지](https://apps.apple.com/us/app/kitchen-stories-easy-recipes/id771068291).

한술에 적용할 원칙: 조리 모드의 주인공은 채팅 로그가 아니라 지금 해야 할 행동과 그 행동의 사진이다. `양파 어떻게 잘라?`가 들어오면 원문에서 확인되는 해당 단계 사진과 설명을 같이 보여 준다. 원문에 원하는 사진이 없으면 다른 음식/완성 사진을 정답처럼 보여 주지 않는다. 사진 없음, 원문에 방법 없음, 이미지 로딩 실패를 각각 솔직하게 표시한다.

### 3. NYT Cooking: 큰 음식 사진, 짧은 제목, 작은 메타/동작 묶음

메인 에이전트는 공식 Google Play 스크린샷 갤러리 두 번째 `White Chicken Chili` 상세 화면을 브라우저에서 실제 확인했다. 흰 바탕에 가로 폭을 채우는 음식 사진, 짧고 검은 제목, 작게 정리된 작성자/시간/평가 행, 작은 빨간 `Save`와 보조 동작 묶음이 관찰됐다. **실제 공식 등록 화면의 시각 관찰**이며 가입/구독/조리 동작을 사용한 결과는 아니다. [공식 Google Play NYT Cooking 등록 페이지](https://play.google.com/store/apps/details?id=com.nytimes.cooking).

한술에 적용할 원칙: 상단 음식 사진은 넓게, 제목은 간결하게, 출처/인분은 작고 정돈되게, 재료/순서는 콘텐츠 탭으로 분리한다. 모든 부분을 색상 카드에 넣지 않고 흰색/크림 여백을 주 바탕으로 유지한다. NYT의 빨간색 브랜딩·사진·아이콘·문구를 복사하지 않고 한술의 따뜻한 오렌지/살구 방향으로 새로 만든다.

### 보조 동작 참고: Mealime의 손 안 대는 조작과 수동 조작 공존

Mealime의 공식 도움말은 조리 지시를 분리해 큰 글씨로 현재 행동을 보여 주며, 손을 가까이 대는 방식뿐 아니라 화면 화살표로 앞/뒤 지시를 이동할 수 있다고 설명한다. 마지막 단계의 완료는 별도의 `Done` 동작이다. 손 안 대는 모드와 수동 이동이 양립하고 이동 자체가 완료는 아니라는 **공식 동작 근거**다. 도움말은 2019-07-29 갱신 문서이므로 최신 앱의 동일 동작을 단정하지 않는다. [공식 Cooking Mode 도움말](https://support.mealime.com/article/88-how-to-use-cooking-mode), [공식 조리 화면 이미지 링크](https://www.mealime.com/images/app-screens/recipe.png), [공식 hands-free 설명 이미지 링크](https://www.mealime.com/images/app-screens/handsfree.png).

한술에 적용할 원칙: 현재 지시를 크게 표시하고 음성 질문과 터치/스크롤이 서로를 막지 않도록 한다. 요리한 사람이 순서를 앞질러 가거나 미리 뒤를 읽어도 된다. AI가 응답 중인 동안에도 다음 단계/타이머에 접근할 수 있어야 한다. 한술에 근접 센서 조작을 새로 추가하자는 제안은 아니다.

주의: Mealime는 공식 홈페이지에서 **2026-10-21 서비스 종료**를 공지한다. 지속 이용을 추천하는 대안 서비스가 아니라 기존 UX 패턴의 참고 사례로만 쓴다. [공식 종료 공지](https://www.mealime.com/closing).

## 한술의 독자적인 밝은 디자인 방향

다음 색상값과 크기는 외부 앱에서 추출한 값이 아니라 **한술을 위한 신규 제안**이다. 파스텔은 배경/보조 표면에 쓰고 주요 글자는 진한 색으로 유지한다.

| 용도 | 제안 색상 | 목적 |
| --- | --- | --- |
| 기본 바탕 | 크림 `#FFFBF4` | 차갑고 회색인 대시보드 느낌을 줄인다 |
| 사진/내용 카드 | 따뜻한 흰색 `#FFFFFF` | 음식 사진을 과도한 장식 없이 살린다 |
| 주요 CTA | 따뜻한 테라코타 `#A94D34` | 파스텔 바탕에서도 글자 대비를 확보한다 |
| 강조 표면 | 살구 `#FBE4D8` | 현재 행동/대화 답변을 부드럽게 구분한다 |
| 보조/타이머 표면 | 연한 세이지 `#E8F0E0` | 현재 조리와 시간 정보의 조용한 구분 |
| 주요 글자 | 짙은 갈색 `#29251F` | 주방에서 떨어져 봐도 읽히게 한다 |
| 보조 글자 | 웜 그레이 `#645D53` | 회색을 너무 연하게 쓰지 않는다 |

곡률 20~28dp, 화면 좌우 여백 20~24dp, 주요 제목 26~30sp, 조리 지시 18~20sp를 출발점으로 삼는다. 색상 대비와 큰 글자/시스템 폰트 배율은 구현 후 검증해야 한다. 그림자·테두리·작은 라벨을 여러 겹 쌓는 것보다 큰 사진, 여백, 글자 위계로 구분한다.

## 화면별 구현 가능한 구조

### 홈/레시피 가져오기

상단에는 `한술`과 작고 조용한 설정 진입점만 둔다. 중심 문구는 `오늘은 뭘 만들어볼까요?`로 한다. 공유 링크가 들어왔다면 링크 입력을 다시 요구하지 않고 로딩/가져온 결과로 이어진다.

직접 진입했을 때는 링크 입력 한 곳과 `레시피 가져오기` 한 가지 주요 동작을 제공한다. 과한 온보딩 설명, 여러 기능 홍보 카드, 모델/서버 디버그 카드는 첫 화면에서 없앤다. 최근 레시피가 실제로 있을 때만 사진 카드로 보여 주고 가짜 추천 레시피나 완성 사진을 채워 넣지 않는다.

### 레시피 상세/조리 전

큰 원문 음식 사진→레시피 제목→출처/작성자→인분 선택→짧은 요리 정보 순이다. 사진이 없으면 사진처럼 보이는 가짜 이미지를 넣지 않고 간결한 빈 상태를 쓴다.

주요 동작은 `요리 시작` 한 개다. 재료는 펼쳐 볼 수 있는 **읽기 전용 목록**이며 준비 완료를 체크하거나 없음을 입력하는 과정을 만들지 않는다. 전체 순서도 미리 읽을 수 있어야 한다. `궁금한 건 편하게 물어보세요`와 작은 음성/텍스트 진입점은 가능하지만 `대체재 찾기`, `재료 추가`, `없어요` 같은 명령 버튼 묶음은 만들지 않는다.

인분 변경은 실제 원문 인분을 기준으로 한다. 물/양념/가열시간도 무조건 비례 적용되는 것처럼 표시하지 않는다. 추정 또는 상담이 필요한 항목의 설명을 인분 선택과 분리해 읽을 수 있게 하고, 특정 라면 예시를 모든 레시피의 수식으로 하드코딩하지 않는다.

### 조리 중

화면 위쪽의 작은 레시피 제목과 `3 / 8 단계`가 문맥을 알려 준다. 가장 넓은 영역은 현재 단계 원문 사진, 바로 아래에는 `양파를 얇게 썰어요`처럼 현재 행동을 크게 표시한다. 원문에 없는 행동을 제목만 보고 만들어내면 안 된다.

다음/이전 이동은 충분히 큰 터치 영역과 스크롤로 가능하게 한다. 완료/건너뜀/되돌리기처럼 의미가 다른 상태 변경은 필요할 때만 보조 동작으로 보이고, 단계를 바라보는 행위로 자동 완료하지 않는다. 진행 중 타이머는 짧은 이름+남은 시간을 가진 세이지색 영역에 표시하며 전체 채팅 기록 속에 묻히지 않는다.

하단에는 얇고 안정적인 대화 도크를 둔다. 음성 준비 상태와 마이크/텍스트 입력 진입점을 포함하되 현재 작업 사진을 압도하지 않는다. 최근 답변 한 덩어리를 짧게 보여 주고 대화 전체는 필요할 때 펼친다. 이 도크는 한술의 독자적 제안이며 삼성/Mealime가 동일한 음성 에이전트 UI를 제공한다는 주장이 아니다.

## 자연 대화에 대한 화면/답변 기준

| 사용자의 말 | 적절한 화면 반응 | 금지할 반응 |
| --- | --- | --- |
| `양파 없는데 괜찮아?` | 현재 요리/투입 단계 문맥으로 생략 영향 또는 대체를 짧게 답한다. 필요한 확인 질문만 한다 | 재료 체크리스트를 열고 먼저 체크하라고 요구 |
| `버섯 좀 더 넣었어` | 사용자 변경 사실을 대화 문맥에 반영하고 익힘/수분 영향이 있다면 설명 | 임의로 다음 단계 완료 처리 |
| `이거 어느 정도 크기로 잘라?` | 확인 가능한 현재 관련 단계 사진과 원문 근거를 보인다. 모호하면 재료만 되묻는다 | 무관한 단계/완성 사진을 잘라낼 크기의 정답으로 사용 |
| `난 이미 볶았는데?` | 해당 사실과 실제 원문 단계를 대조하고 안전한 다음 행동을 안내 | 앞 단계부터 음성 보고를 강요 |
| `두 명인데 물도 두 배야?` | 재료 종류/원문/도구 문맥을 보며 비례가 항상 맞지 않음을 설명 | 어떤 레시피든 무조건 두 배 또는 고정 라면 공식 적용 |
| `좀 타는 것 같아` | 안전 행동/불 상태 확인이 가장 먼저이며 화면에서도 중요한 경고를 명확히 한다 | 사진 찾기나 재료 입력이 안전 안내보다 먼저 |

`언제든 자연스럽게 말하면 모든 상황을 완벽히 해결`한다고 약속하지 않는다. 알레르기, 식품 안전, 원문 누락, 모델 불확실성은 확인 질문과 한계 설명이 필요하다. 이 재설계는 버튼으로 모든 경우를 열거하는 방식이 아니라 대화와 정확한 상태/원문 근거가 결합되는 방식이다.

## 저작권/사진 사용 경계

외부 앱의 스크린샷, 음식 사진, 로고, 아이콘은 참고 링크로만 기록했다. 앱 번들·스토어 소개 이미지·배경 에셋으로 다운로드/복사하지 않는다. 외부 제품의 고유한 일러스트나 전체 화면을 그대로 재현하지 않는다.

만개의레시피 사진도 공개 URL과 출처 표시만으로 재사용 허가가 확보되는 것은 아니다. 사진 사용권 확인은 UI 개선과 별도 과제다. 원문 사진이 없거나 권한/로딩 문제가 있으면 한계를 그대로 보여 주고, AI가 생성한 그림을 원문 단계 사진처럼 위장하지 않는다.
